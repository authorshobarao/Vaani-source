Vaani: Android release-readiness audit

Audit date: November 12, 2026 · Scope: current Android project configuration and source, public production endpoints, and current official Google Play requirements.

Overall: not ready for release sign-off. Android identity, versioning configuration, production connectivity, and the SDK’s default target API are present. Privacy disclosures and permission minimization need work. Signing, the final merged release manifest, remote version history, and Play Console declarations are not verified.

No application code, dependencies, configuration, credentials, or deployment settings were changed. No native release was built, signed, uploaded, or submitted. This report is not a security scan, legal approval, or guarantee of store acceptance.

Priority findings

1. Correct the privacy policy before store submission

  • Audio fallback: the published policy says Vaani does not receive audio recordings. However, hooks/useDictation.ts can record audio and send it to the backend transcription endpoint; artifacts/api-server/src/routes/transcribe.ts forwards audio to Gemini. Disclose that conditional path and relevant processing/retention. The normal native-recognizer path does not make the fallback disappear.
  • Analytics and surveys: lib/analytics.ts creates a persistent random device-scoped identifier and sends usage events and optional survey feedback. The backend analytics route inserts these into database tables. Events include selected preset condition identifiers; custom topics are represented as “custom” rather than their typed label in the inspected selection event. Explain the actual data, purpose, retention/deletion, and sharing, and make Data safety answers match it. Do not describe all server processing as non-persistent.
  • Android backups: introspection sets android:allowBackup="true". Locally stored preparations may be eligible for OS backup unless excluded. Review backup rules and the policy’s “device only” / “deleted when you delete the app” wording. Actual backup behavior and rules in a release are not verified.
  • Health-app requirements: Google requires a Health apps declaration and a comprehensive public policy. For an app not regulated as a medical device, its store description must include Google’s required non-medical-device disclaimer and remind users to consult a healthcare professional. Existing in-app “not medical advice” wording is helpful but does not prove the store listing complies.

3. Finish the release-only checks

  • Confirm package ownership and the highest prior version code in Play Console; confirm the remote auto-increment counter.
  • Confirm Play App Signing/upload-key ownership and certificate fingerprints. No credentials were opened or requested, and no signed AAB was available in the inspected workspace.
  • Inspect the signed release’s target API, final permissions, services, backup rules, debuggable flag, embedded API domain, and absence of a development client.
  • Check all native libraries and packaging for 16 KB page-size compatibility; framework versions alone do not certify third-party native libraries. Consult the current Android guidance and the app’s Console warnings/deadlines.
  • On physical Android or an appropriate emulator, verify cold start/splash, icon masks, safe areas, microphone/camera denial and recovery, selected-file access, PDF/photo report upload, export/share/print, and offline/network failure behavior. No new Android device tests were performed for this audit.
  • Complete Data safety, Health apps, content rating, target audience, store description, screenshots and applicable testing/production-access requirements in Play Console. Account status and declarations were not accessed.

The existing app.config.js dynamically supplies a production-domain fallback; the production profile explicitly supplies the same domain. Runtime source uses that domain, while the development start script intentionally uses a development host. The preview-building script contains Metro/Expo Go/debug metadata; it is not evidence that a separately built native release contains those values. Validate the actual release rather than confusing a preview export with a Play bundle.

Method and limits

Read-only review of app.json, the existing dynamic config and production profile, mobile package declarations, Expo Android configuration introspection, installed direct native-module manifests, React Native SDK defaults, relevant API/dictation/upload/analytics code, and public privacy pages. Public GET requests checked production health and both observed privacy URLs. No purchases, generated AI requests, production data queries, credential access, build submission, or configuration edits were performed.

Introspection runs config plugins but is not the final Android Gradle manifest merge. Dependencies can add permissions absent from app.json and introspection. Remote version counters, third-party processor retention, Play Console settings, and signed-release behavior remain unverified. Findings describe the current reviewed source, not a certification of the existing installed/store binary.
